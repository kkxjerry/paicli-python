# PaiCLI Python 1.1.0 acceptance

Date: 2026-09-01
Release line: `develop` / `v1.1.0`
Product code evaluated: `7022eaa31171867ec3203a1d2c4dc2ebf739058f`
Historical 1.0 product code: `9dc8d1438941f2865655bde99d3c500f80fbb558`

## Decision

PaiCLI Python 1.1.0 is accepted as a local, single-process, real-LLM coding
agent harness with hardened default safety, precise editing/search primitives,
project instructions, diagnostic feedback, provider streaming, persistent
permissions, role-specific model routing, and explicitly configured Skill/MCP/
Web extensions.

The release remains bounded by `SECURITY.md`: it is not an OS-level shell
sandbox, a distributed scheduler, or an exactly-once transaction coordinator
for arbitrary remote side effects.

## P0–P2 completion

### P0 — reachable-path safety and recovery

- destructive command denial is enforced in the base `ToolRegistry`, independent
  of interactive HITL;
- embedded/library runtime is fail-closed unless the caller explicitly opts out;
- oversized, unreadable, or over-budget snapshot files are recorded as skipped
  instead of preventing run startup, and skipped paths are protected on restore;
- iteration, stagnation, and per-Agent Token exits use resumable `STOPPED`
  semantics and keep the current workspace;
- old unreferenced snapshots are pruned while resumable-run snapshots are kept;
- `runtime.capability_matrix()` reports assembled product capabilities;
- MIT `LICENSE` and `NOTICE.md` are present.

### P1 — coding primitives, prompt wiring, and diagnostics

- `replace_text`, `multi_edit`, `apply_patch`, `grep`, and `glob` are production
  tools alongside whole-file write;
- `read_file` supports line ranges and optional SHA-256; edit tools support
  optimistic file-hash checks;
- multi-edit and multi-file patch operations validate all mutations before any
  file is committed;
- HITL collects approvals first, then delegates the approved batch to the
  resource-conflict scheduler;
- `AGENTS.md` / `.paicli.md` is injected into ReAct, Planner, Worker, Reviewer,
  and Aggregator prompts;
- deterministic Python syntax diagnostics and optional stdio Language Server
  diagnostics are returned to the Agent and block completion while errors remain.

### P2 — streaming, permissions, model roles, and extensions

- OpenAI-compatible SSE content/reasoning/Tool Call fragments and Usage are
  reconstructed into the normal Agent Loop protocol;
- exact and glob-shaped permission decisions can be stored locally, while hard
  command policy always has higher priority;
- Planner, Worker, Reviewer, and Aggregator can use separate configured provider
  clients without changing orchestration state transitions;
- Skill, MCP, browser-via-MCP, and Web extensions require explicit configuration;
- Web access requires an allow-list, public DNS, redirect revalidation, and
  bounded responses;
- MCP stdio has request timeout, bounded stderr, notification-before-response
  handling, response-ID matching, and explicit process/PIPE shutdown.

## Comparison with 1.0

The correctness gates are tied in the selected successful 1.0 and 1.1 reports:
3/3 Tasks and 7/7 assertions. The comparison verdict is
`efficiency_improved` because the selected 1.1 report reduced average elapsed
time and configured estimated cost. It also used more input Tokens and Tool
Calls, so this is not a claim of universal efficiency dominance; repeated-run
stability and raw metrics remain the primary evidence.

## Explicit residual boundaries

PaiCLI 1.1.0 does not claim:

- OS-level process, network, filesystem-namespace, or syscall isolation;
- safe parallel code mutation without per-Worker worktrees and merge testing;
- exactly-once behavior for arbitrary remote MCP/Web/API side effects;
- a persistent IDE-grade Language Server workspace;
- full MCP Streamable HTTP/SSE/OAuth/Sampling lifecycle support;
- automatic Tool Retrieval for hundreds of enabled MCP tools;
- Reviewer accuracy calibrated against a human-labelled dataset;
- a Code RAG golden-set Recall@K/MRR benchmark;
- statistically conclusive production reliability from three smoke-suite runs.

Within the stated local single-process trust boundary, P0, P1, and P2 are
accepted for release.
